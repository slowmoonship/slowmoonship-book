# 05｜账户里保存的是余额，还是一份程序？

同一个地址既能收到 ETH，又可能执行代码。以太坊怎样区分这些能力？可以先把账户看作世界状态中的一条记录，再逐项检查它保存的内容。不要从浏览器的图标反推底层结构。

传统账户模型区分外部账户 EOA 与合约账户（Contract Account）。EOA 通过私钥授权顶层请求；合约账户通过部署在地址上的代码响应调用。合约没有一把对应的普通私钥来直接签名发起顶层交易，但代码运行时可以调用其他账户、转移 ETH，甚至创建新的合约。

账户状态的核心字段是 Nonce、Balance、Storage Root 与 Code Hash。Balance 记录该地址的原生 ETH 数量，单位是 Wei；Storage Root 承诺持久存储内容；Code Hash 指向代码的内容摘要。面向使用者，我们也会简写成“地址有代码、有存储”，但代码字节和存储内容并不是完整地塞进这四个字段的显示值里。

两类账户都能持有 ETH。给一个合约地址发钱，可能触发它的代码，能否成功取决于目标执行规则、输入与 Gas。不能认为任何合约都像个人账户一样接受任意转账。另一方面，合约被调用也不一定附带 ETH，顶层 Value 为零照样可能改变大量代币余额。

传统基础模型中，普通 EOA 没有部署的程序代码，持久合约存储主要由合约执行管理。这个入门区别有用，但必须附上版本边界。Pectra 后 EIP-7702 允许 EOA 设置委托标记，调用时执行指定代码。因此，2026 年检查到非空代码，就断言“这是传统部署合约，不能签顶层交易”，已经不成立。

图中把基础字段画在账户旁边，把代币余额画在代币合约的存储一侧。这是本篇最重要的空间关系：你地址的 ETH Balance 与某个 ERC-20 合约记录的“你的代币余额”属于不同位置。两者可以由同一次交易一起改变，不能当成同一个字段。

Account State 也不是一个用户档案。它不自带姓名、邮件、钱包品牌或全部资产列表。资产展示服务要去多个合约和索引数据集读取记录，才能拼成钱包界面。一个地址拥有数十种代币，并不意味着基础账户状态新增了数十个独立的通用余额字段。

数据验证时，可用 `eth_getBalance` 看原生余额，用 `eth_getCode` 看代码，通过合约的 `balanceOf` 读取特定代币余额。读取高度应保持一致。先学会分别提问，我们才能在后面准确理解每一次状态变化。

可以做一个不改变链上状态的对照：对同一地址，在同一块读取原生余额与代码，再对指定代币读取余额接口。即使三个请求都查询同一个地址，它们读取的内容与目标也不同。

代码为空没有为地址提供现实身份；余额为零没有证明地址不存在历史活动。反过来，看到非空代码，也不能在现代主网上跳过委托标记识别。分析工具应保留原始代码判断与分类规则版本，让后来读者知道“账户类型”是怎样推导出来的。
