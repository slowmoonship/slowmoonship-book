# 27｜交易失败了，为什么手续费没有退回来？

你发起兑换，几秒后钱包显示失败，ETH 却少了一点。直觉上，事情没办成就不该收费；网络的结算对象却是已发生的执行与数据处理，不是应用最后交付的业务成果。

被收录而执行失败的交易，节点仍然花费资源检查输入、运行代码和发现错误。Revert 可以撤销相应业务写入，但已经消耗的计费资源按协议结算。发送者 Nonce 也会被使用。因此，同一账户下一次发送通常需要后续序号，而不能假定失败后所有内容都恢复原样。

主动 Revert 与 Out of Gas 又有区别。主动回滚在规则范围内可能保留未使用的可用 Gas；资源耗尽和其他异常会按不同失败规则处理。不能把所有失败交易都写成“必然用满 Gas Limit”，也不能写成“必然只付 21,000 Gas”。

例如兑换合约检查最低输出数量。它可能已经做了一些调用，最后发现价格条件不满足而回滚。保留收据中的失败状态与 Gas Used 能说明收费结果；调用轨迹展示曾经尝试的流程；被回滚的业务日志不会作为成功结果保留。

未收录的请求又是另一种情况。一个节点拒绝了无效签名，或者钱包广播后一直等待，并不自动生成一笔主网执行费。若平台或服务收取其他费用，需要另看服务规则，不能把它混进协议对已收录交易的收费解释。

SQL 汇总失败成本时，先明确统计集合是 `success = false` 的已收录交易，并按时间与费用机制划定范围。若统计失败率，也要说明分母是全部请求、全部已收录交易，还是某协议被识别的调用。Dune 交易表一般不能回答全网所有未收录尝试。

作者 Query 8378486 的已有结果样本在 2026-05-21 记录 32,664 笔失败、2,288,026 笔成功，失败比例约为 1.41%。这是已保存的历史样本，读取日是 2026-10-10，不能改写成“今天全网失败率”。它的成功与失败数量可与相同日期的交易 Query 对齐。

现代账户授权再增加一个例外。7702 有效委托在业务执行前处理，即使后续执行失败，已处理委托仍然保留。讨论“失败但有状态变化”时，必须列出变化来源，不能把协议前置处理与业务转账混成一个口径。

检查一笔失败交易，可以先回答三个问题：是否收录、在哪层失败、收费与授权等协议处理如何结算。这样既能解释为什么 ETH 减少，也不会把失败轨迹中的尝试金额报成最终资金流。

失败率也不能直接用来评判某协议的安全或用户体验。自动化尝试、价格保护、重复提交与攻击流量，都可能形成被收录失败交易。只看到数量变化，尚不足以说明哪个原因占主导。

若要解释某个协议的失败，应先限定目标和函数或业务识别范围，再挑样本检查回滚原因。网络总体失败比例与协议兑换失败比例各有分母；把前者拿来推断后者，会让一个准确的链级数字承载并未取得的应用结论。
