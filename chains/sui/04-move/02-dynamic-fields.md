# 04.2 | Dynamic Field、子对象与数据可见性

如果父对象的 JSON 只有少量固定字段，却承载很多业务状态，Dynamic Fields 是需要继续调查的方向。它允许对象关联在运行中添加、移除的字段，名称可以是符合能力要求的值，而不只是一组写死的字段标识。

普通 Dynamic Field 可以保存具有 `store` 的值。若其中保存 Object，这个值会被包装，外部不能像普通独立对象那样直接按 ID 读取。Dynamic Object Field 要求保存具有对象身份的值，并保持外部按其 ID 查询的可见性。两种形式的状态读取路径不同。[Dynamic Fields](https://docs.sui.io/develop/objects/dynamic-fields)

可见不等于可以独立使用。即使 Dynamic Object Field 的值能被外部查询，事务中通常仍需经父对象及对应 API 访问它，而不是绕过父对象直接当普通输入。分析师要将“查询得到这个 ID”与“执行允许引用这个状态”分开。

一个教学仓位容器可以把很多 Position 关联为动态字段。查父对象得到的是容器身份与固定字段，查字段集合才能了解仓位成员，再读成员内容才能解释数量与资产类型。将容器一行当成完整仓位清单，会漏掉这层状态。

字段名称也有 Type。只比较显示值而忽略 Name Type，可能把不同键空间错误合并。读取动态字段时应保留父对象 ID、名称类型、名称值、字段形式、子对象 ID 或值，以及观察的版本与 Checkpoint。这样才能在历史比较中判断成员是否相同。

父对象当前字段与子对象历史内容不能随意拼接成过去的快照。若 API 只能提供当前成员集合，无法证明过去某个 Checkpoint 的全部成员。历史状态服务、事件与 Effects 可以补充线索，但覆盖不完整时，应明确历史集合的限制。

这也解释了为什么只看 `transaction_objects` 的顶层输入不一定能还原运行时全部子状态访问。动态加载的状态与平台展开方式需要核实。遇到父对象内容未明显改变、却有子对象输出的事务，应先检查动态字段和执行结果，再判断数据是否异常。
