# 06.2 | 显式事件、状态与业务证明

Move Event 是程序显式发出的记录。它可以描述业务动作、金额、对象身份或其他可观察信息，但不会自动覆盖事务里的全部状态变化。一个没有 Event 的成功转移，并不因此缺少真实结果。

Event Type 决定字段结构和含义。`event_json` 是平台提供的 JSON 表示，分析前要核对字段是否存在、数值单位、资产方向和版本变化。Package 或事件结构升级后，同名业务指标也可能需要不同提取逻辑。[Emitting Events](https://docs.sui.io/develop/accessing-data/using-events)

假设教学 Swap 发出 Event E，记录输入 5 SUI 与输出 USDC。要把 E 解释为 Alice 的实际净资金变化，还要确认它属于哪笔事务、事务是否成功、字段代表哪个路由步骤，以及付款和收款主体。Event 里的 sender 或 recipient 也应依具体类型语义判断。

路由事务可能产生多个池的 Swap Event。它们记录沿途成交，不等于多次独立用户提交。直接把每条 Event 金额相加，可能重复计算中间资产周转。分析用户最终投入和产出时，应以事务级边界核对余额或最终资金输出；分析池成交时，才使用每个池步骤的口径。

事件中的 Object ID 是关联线索，不能单独证明此对象被创建或修改。程序可以把既有对象身份写进 Event。想判断对象变化，应再核对 Effects 与版本状态。同样，缺少某类 Event 不能证明对象没有变化，可能只是程序没有发出或平台未覆盖。

事件序号通常在事务内识别位置，因此 `transaction_digest + event_index` 是值得验证的候选键。它不表示 Command 索引，不能假设第 3 条 Event 总是来自第 3 条 Command。一个调用可以发出多条事件，也可能没有事件。

实际业务分类可以保存三层证据：调用目标与参数，成功状态和对象/资金结果，事件类型与字段。只获得第一层时，使用“相关调用”；获得足够结果时，再使用“已完成业务动作”。让结论范围跟着证据走，比给所有名称套上固定标签更可靠。
