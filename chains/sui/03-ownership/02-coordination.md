# 03.2 | 共同排序、对象版本与并行执行

网络排序回答事务如何进入确定的处理顺序；执行依赖回答某笔事务需要等哪些状态准备好。顺序已经确定，并不意味着所有事务都要像单线程程序一样逐笔执行。没有输入冲突的事务可以并行，互相依赖的事务则需要取得正确状态。

当前 Sui 的共同共识流程接受并排序事务，之后执行引擎按依赖推进。官方不同页面中的 Fastpath 描述涉及对象引用、版本与锁定，不能据此把 Address-Owned 事务从当前完整网络生命周期里删除。[Consensus](https://docs.sui.io/develop/sui-architecture/consensus)

普通 Owned 可变输入通常由发送方指定精确版本。如果两份请求同时想修改同一版本，它们并不会因为同属一个用户就自动安全地并行。过期引用、重复使用可变输入和依赖尚未满足，是执行条件问题，而不是调用函数有多复杂的问题。

Shared 输入则使用对象 ID、初始共享版本与可变访问标记等信息。初始共享版本帮助识别共享生命周期，并非请求指定了本次实际读写的精确版本。网络需要根据排序和对象依赖为本次访问准备对应状态。Party 对象同样说明共识版本与“任意地址都能使用”并无必然联系。[Object Versioning](https://docs.sui.io/develop/objects/versioning)

可变访问与只读访问也要分别看。两笔写入同一 Pool 的 Swap 有状态先后关系；读取同一 Immutable Package 不需要同样的写入协调。Shared 只读输入参与相应调度，但不能据此声称它产生对象修改。交易关系表中的出现次数与写入次数应分别定义。

我们的教学 Swap 是一个混合输入事务。它必须满足 Coin 的授权与版本条件，也必须满足 Pool 的共享状态条件，再作为同一 PTB 执行。任何一部分不满足，不能让另一部分单独完成兑换。这是把对象访问图画成“同一事务的条件展开”而非“两笔事务分叉”的原因。

SQL 分析通常能看到输入类别、状态、版本和结果，却未必能得到全部排队延迟。不要用 Shared 对象数量直接估计每笔事务的等待时间，也不要用 Checkpoint 时间差当作执行耗时。性能解释需要实际时间观测与服务指标。
