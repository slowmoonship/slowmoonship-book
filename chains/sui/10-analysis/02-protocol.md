# 10.2 | 协议用户、流动性与可复核分析

协议指标首先需要协议边界。建立经核验的 Package 谱系、函数集合、相关 Object Type 和事件类型，再选择统计单位。Package 调用事务数、池成交步骤数与协议用户数，分别描述不同集合。

一次路由事务可以触及多个协议，也可以多次调用同一协议。按 MoveCall 行数统计表示调用活动；按不同 Digest 表示相关事务；按 Sender 表示所定义的发起地址。若需要业务用户，还应核对代理、账户容器与事件主体，而不能直接改一列名字。

Swap 量也有业务边界。池层面可以统计每个池的实际成交步骤，用户层面则更接近最终投入或产出。多路由中间资产不能重复算成用户总额；价格估值必须使用明确币种与时间，而不是当前价格回填全部历史。

流动性与余额又不能简单互换。集中流动性池的储备、当前价格区间、Position 和费用状态分别提供不同信息。研究本例 Pool 时，coin_a 与 coin_b 能描述选定版本的字段值，但不能单独证明所有区间的有效深度。完整指标需结合协议数学与子状态。[Dynamic Fields](https://docs.sui.io/develop/objects/dynamic-fields)

NFT 与 Kiosk 提供另一种边界例子。对象在容器中、被列售、受转移策略限制或已经成交，是不同状态。对象移动不自动等于销售，某个事件也需核对支付和规则。先掌握对象身份、归属与合约行为，再解释市场数据。[Kiosk](https://docs.sui.io/onchain-finance/kiosk)

可复核分析应交付一个证据包：问题和单位、协议范围及版本、时间窗口、完整 SQL 与参数、执行状态、结果或接口快照、异常与覆盖说明。更新研究时先比较 Schema 与业务定义，再决定是否重跑，不重复消耗额度来获取相同资料。

当数据只覆盖部分 Package 或历史窗口，结果可以使用范围明确的名称。未知不补零，失败不伪装成功，接口核验不冒充 SQL 执行。把限制写清楚不会削弱结果，反而使它能够被另一位分析师准确使用。
