# SUI 09 小结｜每一步都保留证据位置

分析单笔事务，先固定网络、Digest 与历史位置，再读请求、执行状态和费用。随后按需要分别展开对象、调用和事件，不让一对多 JOIN 先改变问题粒度。

案例 A 展示两条原生命令完成 SUI 转移，没有 MoveCall 或 Event。收款金额与发送人净变化之间的差额，可以由 Effects 费用核对。案例 B 展示一笔事务里的多路由、很多调用与事件，以及负净 Gas 结果，说明钱包净变化不自动等于每个成交步骤金额。

案例 C 从 Shared Pool 的创建和早期版本回到 B 的精确前后状态。同一 ID 可以长期保持 Shared 归属，版本与业务字段持续变化；局部第一页不能当作完整生命周期。

这些记录已通过官方只读接口核验，Dune 示例则尚未执行成功。真实案例标识、接口证据、静态 SQL 与执行结果采用不同状态。读者复现时应检查历史覆盖、候选键、分支匹配与数量差异，再登记运行证据。

SQL 的目的，是让状态、事务和业务解释相互校验。能够明确一行代表什么、每个结论来自哪里，以及哪些范围还没有验证，才是可以继续扩展到钱包与协议分析的基础。
