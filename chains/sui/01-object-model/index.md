# SUI 01 | Object Model

## 一个对象，为什么会留下很多行？

如果查到一个 Object ID 对应十条记录，最先要确认的不是有没有重复数据，而是这十条记录分别描述什么。同一对象可以被多笔事务访问，也可以在每次修改后留下新版本。它在历史状态表和事务关系表中反复出现，通常有明确原因。

Object 是 Sui 组织状态的重要单位。Coin、NFT、流动性仓位和权限凭证都可以是 Move Object。每个实例有自己的身份；Move Type 说明它属于哪种结构，Owner 说明它如何被访问，Version 与 Digest 则用于识别和承诺某个状态。发布的 Move Package 也以对象形式存储，但内容是代码与相关元数据，不能和普通业务对象混为一谈。[Object Model](https://docs.sui.io/develop/sui-architecture/object-model)

数据库类比能解释一部分：Object ID 像稳定的实体标识，版本像实体的历史状态位置。类比到这里就应停下。Sui 对象还参与协议授权和执行依赖；向事务提供某个 Object Reference，是对具体状态的引用，不能把它理解成“随便取出数据库当前一行”。

例如 Alice 将一张 NFT 转给 Bob，NFT 的 ID 可以保持不变，Owner 与 Version 发生变化。用 `COUNT(DISTINCT object_id)` 可以描述涉及多少不同对象；用对象版本行数描述的则是历史记录数量。两种统计都可能正确，前提是问题不同。若把前后两版都当作当前存量，就会把同一 NFT 算两次。

还要区分“对象存在于历史”与“对象当前可以独立访问”。对象可能被包装在另一对象中，后来又被解包；也可能被删除，留下历史证据。一个旧版本能在归档中查询，并不意味着它能再次作为新的可变输入。查不到当前对象，也不足以证明它从未存在。

本模块建立两个阅读习惯。第一，描述对象时同时保留身份、版本、类型和访问状态。第二，把对象内容与“谁在哪笔事务中使用它”的关系分开。前者帮助理解状态，后者帮助理解行为。

回到两张总地图，Runtime Map 中的输入和输出通过对象身份相连，Data Map 中的多行记录则沿着对象版本与事务形成历史线索。学会这两个方向，才能回答“这个对象现在是什么”和“它为何变成这样”两个不同问题。
