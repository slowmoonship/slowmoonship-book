# 08.3 | 候选键、覆盖率与 JOIN 放大

Schema 核验只能证明列名和类型，不能证明数据唯一、完整或新鲜。把 transaction_digest 称为逻辑标识，与断言数据库已经有唯一约束，是不同强度的结论。分析前应查空值、重复与匹配覆盖。

候选键可从记录粒度提出：Checkpoint Sequence、Transaction Digest、Digest 与 Event Index、Object ID 与 Version。MoveCall 和对象关系的候选组合还要依据平台展开方式检查。不要遇到重复就先 DISTINCT，否则可能把真实角色或多次调用删掉。

JOIN 放大是一种数学后果。某 Digest 有两条调用和四条对象关系，将两者相连就可能产生八条组合。再接两条事件，会变成十六条。COUNT(DISTINCT Digest) 能恢复事务数，却不能让 SUM(金额) 自动正确；每个金额仍可能被复制多次。

需要多个指标时，先将各分支聚合到目标单位。调用分支按 Digest 统计调用数；对象分支按明确角色统计关系行或不同 ID；事件分支按所选类型统计事件数。汇总后再连接事务主干，可以避免明细组合复制。

如果分支只是筛选条件，使用 EXISTS 常能保持主干粒度。例如找包含某 Package 调用的事务，不必先把每次调用展开为一行。若真的需要调用明细，结果粒度就明确改为一次记录的调用。

覆盖率检查则应保留未匹配。对象关系没有状态内容，可能涉及删除标记；事件没有主干记录，可能是窗口或摄取不同步。记录未匹配数量并按状态、日期和来源分类，可以帮助区分合法空缺与数据问题。

最新性和历史范围不能只读最大值。一个表的最新 Checkpoint 到达较高位置，并不证明中间没有断点；抽样日期能证明该样本可查，不证明创世至今全部完整。对数据连续性、重复和模式变化的检查，应在有成本控制的窗口内逐步完成。[Data Freshness](https://docs.dune.com/data-catalog/data-freshness)

本书的静态 SQL 保留这些方法，但当前 402 限制使执行证据缺失。使用者应先核实窗口与额度，再运行验证；不能把 STATIC_CHECKED 视为已通过真实数据测试。
