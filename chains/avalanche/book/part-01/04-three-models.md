# 04｜三条链为什么不能共用一张转账表？

如果业务只问“谁给谁转了多少钱”，分析师很容易设计一张 `from、to、amount` 表。到了 Avalanche，这张表会同时丢掉三种信息：EVM 执行层次、平台操作的对象，以及 UTXO 的消费与生成关系。

## 账户、平台与输出集合

C-Chain 采用账户与 EVM 状态模型。一次签名交易提供发送者、目标、原生币数量和输入字节；执行后产生收据，合约可以发出日志。代币余额由相应合约维护，调用过程可通过追踪服务重建。因此顶层 `to` 往往是合约，而不是最终代币收款人。

P-Chain 由 PlatformVM 定义状态转换，既有资金输出，也有网络与验证者对象。一次创建链操作需要表达网络归属、VM 与 Genesis；一次委托需要表达节点、锁定金额、时间与奖励所有者。将它们解析成普通 EVM 调用，会制造不存在的合约地址与事件语义。

X-Chain 由 AvalancheVM 处理资产交易，采用未花费交易输出（Unspent Transaction Output，UTXO）模型。交易消费既有输出，生成新输出。一个付款可以使用多个输入，又同时生成收款输出和找零输出。把输入地址和输出地址两两连接，会凭空放大转账条数。

三者的共同点是按各自规则接受操作并维护状态。差异在于状态的组织和操作的语义，不在于哪种模型更“先进”。账户模型让合约维护复杂可变状态；UTXO 模型明确标出资金消费来源；平台模型直接承载网络管理对象。

## 一个统一表需要承认损失

为展示跨链活动，可以建立教学性的统一活动表，保存网络、区块链、交易类型、时间和来源路径。但这个表是规范化视图，不是某个 RPC 原生返回的万能 Schema。详细输入、输出、日志和注册仍应保留在各自子表。

例如“金额”至少要附上资产身份和单位。C-Chain 原生 AVAX 的 EVM 数量以十八位小数对应的整数表示，P/X 资产接口中的 AVAX denomination 为九。直接加原始整数，会把单位差异变成九个数量级的错误。显示成 AVAX 后，也仍需区分本金、费用、锁定与在途。

统一字段还不能替代经济含义。Export 和 Import 是同一跨链移动的两侧记录，记录数为二不等于发生两次独立付款。消息事件可能不涉及资产；验证者权重可能由 L1 自定规则产生，不一定表示 AVAX 数量。

## 数据落地从边界开始

本篇对 C-Chain 使用 Dune 的实际表与字段，对 P/X 使用官方 JSON 响应。后文的 Python 仅把已保存样本提取成明确的局部视图。没有公开 API 的网络，就保留观察缺口，不替它构造假的 EVM 日志。

读者可以先记住三个问题：交易请求什么，运行规则改变什么，来源实际记录什么。把这三问带到每条链，比记忆一张巨大的字段表更可靠。下一部分会进一步解释：是谁决定接受交易，又是谁解释交易的含义？

规范化表还应保留 transaction_type。这样读者看到一条资金相关记录时，可以回到它所属的链与操作规则，判断它是普通支付、锁定、注册费用还是跨链导出。省掉类型虽然让表更短，却会使后来所有金额分析依赖猜测。
